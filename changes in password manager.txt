VulnLab Transformation - Changes in Password Manager
=====================================================

Project:
VulnLab, an intentionally vulnerable password-manager application for local
and authorized cybersecurity training.

Important:
This application is intentionally vulnerable. Use only synthetic credentials
and demo data. Test only the local VulnLab instance or an environment for
which explicit authorization has been granted.


1. Application rebranding
-------------------------

Changed:
- Replaced the PassOP branding with VulnLab.
- Updated the browser title to "VulnLab - Password Security Training Lab".
- Updated the navbar, main page heading, and footer branding.
- Added an intentional-vulnerability warning to the interface.
- Replaced the original README with VulnLab setup, architecture, testing,
  remediation, and authorized-use documentation.

Main files:
- src/components/Navbar.jsx
- src/components/Manager.jsx
- src/components/Footer.jsx
- index.html
- README.md

Effect in VulnLab:
- The application now clearly identifies itself as a cybersecurity training
  laboratory instead of a normal production password manager.
- Users are warned that the application must only be used locally or with
  authorization.
- Existing password-manager CRUD behavior remains available.


2. IDOR and broken access control lab
--------------------------------------

Changed:
- Added synthetic ownership through the X-VulnLab-User request header.
- Added vulnerable record access and deletion endpoints.
- Added secure ownership-scoped comparison endpoints.
- Added documentation for IDOR and broken access control.

Vulnerable endpoints:
- GET /api/lab/vulnerable/passwords/:id
- DELETE /api/lab/vulnerable/passwords/:id

Secure endpoints:
- GET /api/lab/secure/passwords/:id
- DELETE /api/lab/secure/passwords/:id

Effect in VulnLab:
- A caller using the vulnerable route can access or delete another user's
  record when the record ID is known.
- The secure route checks both the record ID and ownerId.
- Cross-user access is rejected by the secure implementation.
- This demonstrates that authentication or caller identification alone is not
  enough; every resource operation also needs authorization.


3. NoSQL injection lab
----------------------

Changed:
- Added a vulnerable MongoDB search endpoint that accepts a complete
  caller-controlled filter object.
- Added a secure search endpoint that accepts only a string site value.
- Added type validation, regular-expression escaping, ownership enforcement,
  and response projection to the secure search path.

Vulnerable endpoint:
- POST /api/lab/vulnerable/search

Secure endpoint:
- POST /api/lab/secure/search

Effect in VulnLab:
- The vulnerable endpoint allows MongoDB query operators or an ownerId
  override to influence the database query.
- The secure endpoint constructs the query on the server and keeps the
  ownership condition outside user-controlled input.
- The secure endpoint returns only id, site, and username.


4. Stored XSS lab
------------------

Changed:
- Added a notes field to password records in the frontend.
- Added an intentionally unsafe notes preview using
  dangerouslySetInnerHTML.
- Added a secure comparison preview using normal React text rendering.
- Added stored-XSS documentation.

Main file:
- src/components/Manager.jsx

Effect in VulnLab:
- User-controlled notes are stored with password records.
- The vulnerable preview interprets stored markup as HTML.
- The secure preview displays the same content as text and applies React
  output escaping.
- This demonstrates why untrusted stored content must not be inserted into
  HTML without appropriate sanitization.


5. Reflected XSS lab
---------------------

Changed:
- Added support for the q query parameter in the frontend.
- Added a vulnerable reflected preview using dangerouslySetInnerHTML.
- Added a secure reflected preview using escaped React text rendering.
- Added reflected-XSS documentation.

Example local URL:
- http://127.0.0.1:5173/?q=local-demo

Effect in VulnLab:
- Query-string content is reflected into the page.
- The vulnerable preview demonstrates unsafe HTML insertion.
- The secure preview renders the value as literal text.
- This demonstrates the need for context-appropriate output encoding.


6. Sensitive data exposure lab
------------------------------

Changed:
- Added a vulnerable export route that returns complete password documents.
- Added a secure export route that uses a MongoDB projection.
- Added documentation describing excessive API data exposure.

Vulnerable endpoint:
- GET /api/lab/vulnerable/export

Secure endpoint:
- GET /api/lab/secure/export

Effect in VulnLab:
- The vulnerable response exposes plaintext passwords, ownerId, MongoDB _id,
  and other stored fields.
- The secure response returns only id, site, and username.
- This demonstrates why API responses should contain only the fields required
  by the client.


7. Weak authentication controls lab
------------------------------------

Changed:
- Added an isolated synthetic demo account.
- Added a vulnerable login endpoint without rate limiting.
- Added a secure login comparison endpoint with derived password comparison,
  timing-safe equality, generic errors, and rate limiting.
- Added synthetic in-memory token generation.
- Added authentication documentation.

Demo account:
- Username: demo-user
- Password: VulnLab-demo-only

Vulnerable endpoint:
- POST /api/lab/auth/vulnerable/login

Secure endpoint:
- POST /api/lab/auth/secure/login

Effect in VulnLab:
- The vulnerable endpoint processes unlimited failed login attempts.
- The secure endpoint returns HTTP 429 after more than five attempts per
  minute from the same IP address.
- Successful secure login clears the failed-attempt counter.
- The demo account is synthetic and must not be reused anywhere else.
- The training header and in-memory tokens are not production authentication.


8. Insecure input validation lab
---------------------------------

Changed:
- Added a vulnerable record-creation endpoint that accepts arbitrary object
  fields and weak values.
- Added a secure record-creation endpoint with server-side validation.
- Added an explicit field allowlist.
- Added type checks, length limits, HTTP/HTTPS URL validation, and notes
  validation.
- Added input-validation documentation.

Vulnerable endpoint:
- POST /api/lab/vulnerable/records

Secure endpoint:
- POST /api/lab/secure/records

Effect in VulnLab:
- Weak or malformed records can be stored through the vulnerable route.
- Unexpected fields are accepted by the vulnerable route.
- The secure route rejects invalid values and unexpected fields.
- The secure route adds ownership information on the server rather than
  trusting a client-supplied ownerId.


9. Security headers and information disclosure lab
---------------------------------------------------

Changed:
- Added secure headers to /api/lab/secure/* routes.
- Removed X-Powered-By from secure lab responses.
- Added Content-Security-Policy.
- Added X-Content-Type-Options.
- Added X-Frame-Options.
- Added Referrer-Policy.
- Added Permissions-Policy.
- Added vulnerable and secure diagnostics endpoints.
- Added security-header documentation.

Diagnostics endpoints:
- GET /api/lab/vulnerable/diagnostics
- GET /api/lab/secure/diagnostics

Effect in VulnLab:
- The vulnerable diagnostics response exposes Express, Node.js version,
  operating system, database name, environment, and route structure.
- The vulnerable response retains Express framework disclosure.
- The secure response returns only a stable service health result.
- Secure headers reduce browser attack surface and unnecessary information
  disclosure.


10. API security review and mutation lab
-----------------------------------------

Changed:
- Added a vulnerable update endpoint that does not verify ownership.
- Added a secure update endpoint with ownership enforcement.
- Added writable-field allowlisting and string validation.
- Added API security documentation and endpoint coverage notes.

Vulnerable endpoint:
- PUT /api/lab/vulnerable/passwords/:id

Secure endpoint:
- PATCH /api/lab/secure/passwords/:id

Effect in VulnLab:
- The vulnerable route allows a caller to update another user's record when
  the record ID is known.
- It also accepts arbitrary fields, including protected fields such as
  ownerId.
- The secure route rejects unexpected fields and returns 404 for a record that
  does not belong to the caller.
- This demonstrates authorization, mass-assignment, and API input-control
  failures.
